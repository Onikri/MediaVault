# Серверный LMT и MangaJaNai

Работа продолжается в ветке `codex/manga-backend-processing`. Это ещё не
подтверждение полного переноса всех функций и не отчёт о развёртывании на Oracle.
По выбору владельца поддерживаются локальные модели и собственный LLM endpoint;
Gemini и отправка изображений Google исключены.
По уточнению владельца текущий приоритет — серверные замеры полного LMT с LaMa
и переводом, без апскейла. Работы и замеры MangaJaNai отложены.

## Текущая цепочка

Читалка отправляет страницу в авторизованный backend. Очередь выполняет
RT-DETR/ComicTextDetector → script gate → выбранный OCR → собственный LLM →
Fast/LaMa → MangaJaNai → набор текста. При совместном режиме OCR видит оригинал,
а нейросеть апскейлит очищенный рисунок до набора перевода. Разрешено включать
апскейл отдельно. Исходный CBZ в Drive не переписывается.

`lmt/upstream/lib/components/Overlay.svelte` и его компоненты перенесены из
LMT `39a95be1890e2ea3e227052976bbaf576a8eb7b3`: области, порядок чтения,
undo/redo, правка текста и оформления, raw/cleaned/result, дополнительные
inpaint-патчи и восстановление оригинала, JPG-экспорт. Web adapter убирает
зависимость редактора от расширения. На маленьком экране панель переносится
на несколько строк. Шрифты поставляются локально; можно загрузить свой шрифт.

Google/OAuth-токены и ключ библиотеки не поступают в Chromium LMT. Он получает
только страницу и настройки. URL, модель и API key LLM выбирает оператор backend;
клиент не может подставить произвольный endpoint. Исходящие запросы браузерного
процесса ограничены статическими ресурсами, загрузками моделей и LLM-прокси.

Задания разделены по владельцу. Результаты хранятся в RAM до 10 минут,
суммарно до 128 МиБ строк изображений; истёкшие записи удаляются фоново.
В читалке — до 5 результатов / 64 МиБ буферов. Отмена закрывает страницу
инференса LMT; PyTorch завершает текущий тайл и прекращает обработку. Модельные
веса и профиль CacheStorage сохраняются на диске backend.

## Запуск

Сборка из корня репозитория, Node.js ≥22.12:

```sh
npm ci
npm run build
python -m venv .venv
# Установи подходящие CPU/CUDA PyTorch wheels прежде остальных зависимостей.
python -m pip install torch==2.10.0 torchvision==0.25.0 --index-url https://download.pytorch.org/whl/cpu
python -m pip install -r server/requirements-manga.txt
python -m playwright install chromium
python scripts/install-mangajanai.py --directory /private/data/mangajanai
```

Установщик по умолчанию загружает все 14 MangaJaNai V1 и IllustrationJaNai
V3 denoise PTH. `--list`, `--archive <имя>` и `--all` позволяют установить остальные
стабильные выпуски из зафиксированного manifest. Проверяются размер и SHA-256;
архивы извлекаются через промежуточную папку, пути выхода запрещены. Лицензия
моделей — CC BY-NC 4.0. Исходники интеграции не содержат весов.

Настройки приватного окружения сервера:

```dotenv
DATA_DIR=/private/data
LMT_LLM_URL=http://127.0.0.1:8081/v1
LMT_LLM_MODEL=your-local-model
LMT_LLM_SCHEMA=openai
LMT_LLM_API_KEY=
MANGAJANAI_MODEL_DIR=/private/data/mangajanai
MANGAJANAI_DEVICE=cpu
OMP_NUM_THREADS=2
MKL_NUM_THREADS=2
```

В Docker LLM должен быть доступен из контейнера. Его loopback отличается от
loopback VM; используй имя сервиса в приватной Docker-сети. Endpoint LLM не
публикуется в интернет. Поддерживается также upstream-схема `lmstudio`.
Сборка backend теперь использует корень checkout:

```sh
docker build -f server/Dockerfile -t mediavault-reader .
```

Существующий `update-existing.sh` учитывает новый build context. Изменения не
перезапускают и не заменяют уже работающий сервер сами по себе.

## API

| Запрос | Назначение |
| --- | --- |
| `GET /reader/processing` | Готовность LMT, установленные модели MangaJaNai |
| `POST /reader/jobs` | Создание задания: base64 `image`, объект `options` |
| `GET /reader/jobs/{id}` | Состояние, прогресс, готовый результат |
| `POST /reader/jobs/{id}/cancel` | Отмена и удаление результата |

Изменения/получение результата требуют существующей owner session. В `options`
разрешены перевод и апскейл, язык, OCR, детектор, inpaint, масштаб, модель,
тип страницы и тайл. Редактор использует операции `detect`, `translate`,
`inpaint` и ограниченный список областей. Страница — до 10 МиБ / 24 Мп;
результат апскейла — до 100 Мп. Длительность задания ограничена 15 минутами.

## Замеры и проверки

`scripts/benchmark-reader.py` фиксирует архитектуру, фактические ресурсы,
хеш входной страницы, параметры, длительность и пик суммы RSS процесса и детей.
Отдельную LLM включают через `--include-pid`. Общие страницы памяти могут
учитываться несколько раз; это не измерение уникальной физической RAM.
`--save-result` сохраняет приватный preview только по явному параметру.
Для полного LMT в отчёт входят отдельные `detectionMs`, `ocrMs`,
`translationMs`, `inpaintMs`, `typesetMs` и фактический метод очистки каждой
области. `quality` не считается выполненным LaMa, если upstream перешёл на
Fast. `firstRunInProcess` означает первый прогон текущего процесса;
дисковый кеш при этом может быть заполнен ранее.
Неуспешный прогон сохраняется с `success=false`, временем до ошибки и последним
этапом; он не считается скоростью готовой страницы. Для ограниченного вывода OCI:
`python scripts/summarize-reader-benchmark.py /private/data/benchmark/lmt-4b-a1.json`.
Полные изображения и transcript по умолчанию в краткий отчёт не включаются.

`benchmark-reader.sh <SHA> prepare-lmt` собирает окружение без установки
апскейл-моделей. `benchmark-lmt.sh <SHA> prepare 4b` готовит официальный
llama.cpp b11887 и Qwen3-4B-Q4_K_M с проверкой SHA-256. Затем `lmt 4b`
измеряет CTD → Manga-OCR → свой LLM → LaMa → набор русского текста дважды.
LLM и браузерный backend работают в отдельной Docker-сети без публикации портов;
лимиты — 6 ГиБ для LMT и 4 ГиБ для LLM, всего на VM остаются те же 2 CPU.
Запуск ожидает load1 ≤ 1,5 и не менее 10 ГиБ доступной памяти до 180 секунд.

Реальные локальные прогоны 2026-10-25, Windows AMD64, CPU 2 threads:

| Цепочка / страница 1715×2417 | Первый / повторный запуск | Пик суммы RSS |
| --- | --- | --- |
| IllustrationJaNai V3 denoise FDAT M 2×, тайл 128 | 219,7 / 213,1 с | 607 МиБ |
| LMT Japanese Paddle → Qwen3 0.6B Q8 → Fast | 38,6 / 17,6 с | 2,46 ГиБ, включая LLM |

Это замеры локального x86 CPU в рабочем окружении, а не Oracle A1. LMT нашёл
3 области, но визуальная проверка показала ошибки OCR/смысла, повторы и остатки
исходного текста на рисунке. Qwen 0.6B не подтверждена как подходящая модель
для японского → русского. Отдельный полный прогон с Qwen3 4B, Manga-OCR и LaMa
на A1 приведён ниже; в 4B переводе тоже остаются смысловые пропуски.

Дополнительная локальная проверка CTD + Manga-OCR + Qwen 0.6B + LaMa завершилась
за 116,897 с, пик суммы RSS вместе с LLM — 5,37 ГиБ; все 3 области имеют
`method=lama`, без Fast fallback. Исходный японский текст теперь распознан
полными репликами; слабая LLM по-прежнему ошибается в русском переводе.
Это проверка работоспособности: для совместимых ONNX-операторов действовал
автоматический выбор WebGPU/WASM, поэтому она не является чистым CPU-замером
и не используется как оценка производительности Oracle.

Через авторизованную Oracle Cloud Shell подтверждены A1 Flex, 2 OCPU, 12 ГБ RAM,
Ampere Altra, GPU отсутствует. `deploy/oracle/measure-existing.py` использует
уже включённый Run Command, без выдачи новых ключей или изменения тарифа.
`measure-inventory.sh` читает RAM, load, диск, Docker stats и health. Замеры
самого inference приведены в [отдельном отчёте Oracle A1](oracle-lmt-benchmarks.md).

Первичная диагностика VM: aarch64, 2 CPU; MemTotal 12 213 568 kB,
MemAvailable 10 734 276 kB, swap отсутствует, load 0,095 / 0,102 / 0,040.
Свободно 34 ГБ из 48 ГБ. Importer: 741,8 МиБ, CPU 0,90%; HTTPS: 33,98 МиБ,
CPU 0,12%. Это реальный выполненный Run Command, exit 0.
`benchmark-reader.sh <SHA> prepare` собирает отдельный образ и модельный каталог;
`upscale` запускает контейнер с 2 CPU / 4 ГиБ RAM, без private volume production.
Первая ARM-сборка прошла; подготовка обнаружила недоступный пользователю vault
каталог `/app/scripts`. Dockerfile исправлен и теперь проверяет чтение manifest
и запуск benchmark inventory от vault при сборке. Полный LMT с Manga-OCR,
Qwen3 4B и LaMa прошёл дважды после увеличения лимита LMT с 4 до 6 ГиБ:
4 ГиБ приводили к подтверждённому cgroup OOM при OCR.

`test_reader_processing.py` проверяет авторизацию, изоляцию, очередь, отмену,
истечение результатов, декодирование и сборку тайлов. Численный тест тайлов
использует fixture и не считается нейросетевым инференсом. `processing-browser.cjs`
проверяет реальные UI/MessageChannel/editor lifecycle с API fixture на 360/1280 px,
включая исправление реплики и применение в читалке. Старые LMT/манга-тесты
сохранены. Полный Python suite локально имеет Windows-ошибки POSIX permissions,
блокировок SQLite и fMP4 fixture. Linux CI для `98dfb0f` успешно выполнил сборку,
72 Node-теста, серверный набор из 161 теста и браузерные проверки, включая редактор
на 360/1280 px. CI проверяет контракты; реальная нейросетевая обработка приведена
отдельно выше.

## Что ещё нужно подтвердить для полного переноса

- Качество и полный текст на EN/JP/KR страницах, LaMa и обеих моделях детекции.
- Все семейства стабильных MangaJaNai/IllustrationJaNai; сейчас реальный прогон
  подтверждает все 19 PyTorch-моделей из V1 manga и V3 denoise на маленьком изображении;
  замер полной страницы выполнен для FDAT M 2×. ONNX-варианты могут требовать GPU/bfloat16 runtime.
- Полное управление модельным кешем, подготовкой и паузой/возобновлением загрузок.
- Пользовательский контекст/словарь тайтла, настройки GPU по подсистемам
  и диагностический экспорт. Апскейл после ручного редактирования сохраняется;
  браузерная проверка подтверждает итоговую ширину и параметры запроса.
- Обновление рабочего backend существующей VM с сохранением OAuth/очереди.
  ARM-образ и изолированный полный LMT на A1 уже проверены.

Эти пункты остаются частью активной цели; проход базовых тестов их не заменяет.

## Файлы Codex на D

В Windows перед командами выполняется `. ./scripts/cache-env.ps1`: npm, pip,
Hugging Face, Torch, Playwright, pycache и temp направлены в `.codex-local/`.
`scripts/start-project-codex.ps1` запускает новый Codex с project-local
`CODEX_HOME`. Локальная `.codex/config.toml` задаёт каталоги SQLite/log и
исключена из Git. Уже запущенное desktop-приложение не переносит свою историю
и общие кеши от изменения переменной дочернего процесса; launcher применяется
при новом запуске. Документация: [Codex config/state locations](https://developers.openai.com/codex/config-advanced/).
