# Процессор текста и инпейнт читалки

## Этапы

1. JSON перевода хранится независимо от растрового результата. Для новой
   очистки или смены шрифта повторный запрос к Google не требуется.
2. Процессор проверяет координаты, размеры, пересечения, русский текст,
   загружает кириллические шрифты и подбирает кегль/переносы до очистки.
   Длинные слова получают аварийный перенос; числа и URL не меняются.
3. Все маски строятся из неизменного оригинала, в кропах с контекстом 24 px.
   Бумага оценивается по ближнему кольцу вокруг текста. Крупные связные
   компоненты рисунка отбрасываются; доля маски ограничена 60% кропа.
4. Инпейнт работает только по маске букв. «Авто» использует заливку на
   плоском фоне и LaMa на сложном; «LaMa» направляет все безопасные области
   модели; «Быстро» оставляет адаптивную заливку и защищённый Telea.
5. Очищенные фрагменты компонуются по маскам. Русский текст рисуется только
   после всех проходов очистки — соседняя область больше не стирает уже
   набранные буквы. Рисование ограничено рамкой вёрстки.
6. Ошибка одной области оставляет её оригинал и сохраняет полный перевод
   под страницей. Остальные области продолжают обработку. Счётчик показывает
   реально набранные области; предупреждения не выдаются за полный успех.
7. Готовая WebP-страница кэшируется отдельно с профилем инпейнта и шрифта.
   Полный JSON/изображения диагностического запроса в этот кэш не попадают.
   Повтор очистки использует JSON; явный «Повторить без кэша» отправляет Google.

Модули: `manga-cleaning.js` — маски и композитинг, `manga-typeset.js` —
измеренная вёрстка, `manga-renderer.js` — этапы, `manga-lama.js` — ленивый
адаптер upstream LaMa. Вычисления выполняются в ES-module Web Worker.
LaMa использует WASM: используемый FFC-граф несовместим с WebGPU.
Веса 206 291 843 байта проверяются upstream SHA-256 и кэшируются браузером.

## Проверки

`npm run test:cleaning` проверяет настоящие Canvas/Worker/шрифты, плотную
маску, сохранность соседнего рисунка и локальный отказ модели.
`MANGA_REAL_LAMA=1 npm run test:cleaning` дополнительно выполняет настоящий
инференс LaMa WASM с закреплёнными весами из локального тестового кэша.
В фактическом холодном прогоне CaaS x86_64 одна область заняла 190 113 мс
включая загрузку/инициализацию и нейросеть. Это не время тёплого инференса,
не замер телефона/Oracle и не результат Google. Автопрофиль не загружает
нейросеть для обычных плоских речевых пузырей.

## Профиль Gemma

Отчёт пользователя показал: тело около 162 КБ, отправка 218 мс, затем
отсутствие HTTP-ответа до 30-секундного тайм-аута. Размер inline-запроса
существенно ниже 20 МБ. Старый обработчик ошибочно регистрировал status=0
при завершении тайм-аута как заголовки: теперь заголовки требуют status>0.
Отчёт не различает очередь провайдера и генерацию до буферизованного ответа.

Нативный профиль Gemma использует `streamGenerateContent?alt=sse`, короткие
кортежи `[номер_блока, русский, шрифт, тип]` и prompt-only JSON вместо
принудительного responseMimeType. MINIMAL остаётся выключением thinking,
как описано в официальной документации Gemma. ID и полнота ответа проверяются
после восстановления порядковых номеров. Поток сообщает число событий,
символов и законченных реплик; thought-части не отображаются. Тайм-аут
ожидания новых данных и общий предел отделены: 30 / 90 сек по умолчанию,
не более 120 сек при настройке вручную. Автоматической подмены на Flash нет.
Для сравнения сохранён профиль обычного JSON-запроса.

Потоковый контракт и компактное отображение проверяются fixtures, не личным
API-ключом пользователя. Реальное ускорение Gemma после изменения требует
повторного запроса в его браузере. Рабочий Flash-профиль не переводится
на экспериментальный транспорт.

Источник: https://ai.google.dev/gemma/docs/core/gemma_on_gemini_api
