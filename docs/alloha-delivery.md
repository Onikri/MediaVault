# Доставка Alloha

## Восстановление и запуск выбранного качества — 6 ноября 2026

Старый iframe `absciss.thealloha.club` при живой проверке вернул HTTP 404
с сообщением об отсутствии контента. Это ошибка конкретной ссылки, а не
доказательство блокировки IP или браузерного профиля. Ответы 404/410 теперь
прерывают ожидание готовности плеера сразу. Некорректные страницы и метаданные
дают короткую паузу для этой ссылки, без увеличения счётчика отказов профиля.
Настоящие отказы 401/403/429 сохраняют прежнюю обработку и карантин.

Ветка сайта `/online/prepare` проверяет первый медиасегмент только выбранного
качества активной озвучки. Остальные опубликованные качества остаются в меню
как метаданные; выбор другого качества запускает его отдельную проверку.
Публичный `/resolve` по-прежнему проверяет все выданные ссылки на качества.
В одном сравнении на Oracle подготовка выбранного 2160p заняла 7,79 с вместо
39,44 с при обходе всех вариантов. Это отдельные живые замеры, не гарантия SLA.

Если варианты Alloha исчерпаны, интерфейс один раз обновляет обнаружение
источников. Появление нового варианта той же озвучки повторяет подключение;
пополнение списка во время здорового воспроизведения его не перезапускает.
Подмена UA и других параметров внутри живой сессии не добавлялась.

Проверки: `test_alloha_delivery.py` — 15 контрактных тестов на Python 3.12;
`alloha-recovery-browser.cjs` — браузерный контракт обновления устаревшей ссылки;
Node player/watch/lease — 20 тестов; production build выполнен. Контрактные
проверки используют поддельный источник и не являются проверкой внешнего CDN.
Живая проверка Oracle отдельно подтвердила готовность настоящего первого
медиасегмента выбранного 2160p. Нейросетевые модели здесь не используются.

Сервис работает в одном процессе Python 3.12 с FastAPI и uvicorn. Модуль
`server/alloha_delivery.py` содержит resolver и HLS-прокси. Основной API
подключает его к существующему плееру через отдельную ветку Alloha в
`online_sessions.py`. Остальные адаптеры используют свой прежний путь.

## Запуск отдельно

Установить `server/requirements-service.txt` и системные зависимости из
`server/Dockerfile`. Нужны Chromium, `dpkg-deb`, `gpgv` и Debian archive keyring.
Основной сервер уже содержит эти зависимости.

```sh
cd server
DATA_DIR=/path/to/checkout/.codex-local/alloha-data \
ALLOWED_ORIGIN=https://onikri.github.io \
uvicorn alloha_delivery:app --host 127.0.0.1 --port 7864 --workers 1 --no-access-log
```

Reverse proxy должен направлять `/resolve`, `/play/*`, `/hls/*` в этот
процесс. При подключении к основному API используется существующий порт 7860.
Однопроцессный запуск обязателен для общего лимита двух потоков на внешний
адрес. Отдельный сервер авторизации в этот модуль не входит.

```sh
curl --get https://YOUR_DOMAIN/resolve \
  --data-urlencode 'iframe=https://alloha.yani.tv/?YOUR_PUBLISHED_IFRAME_PARAMETERS'
```

Ответ содержит ровно `sid`, `active_id`, `skip`, `subtitles`, `translations`.
В каждой озвучке доступны `id`, `name`, `default`, `qualities`, `play`.
Ссылки `play` имеют вид `/play/{sid}/{audio}/{q}.m3u8`. Их можно передать
обычному hls.js или ffplay. Клиенту достаточно адреса нашего сервиса.

`u` в `/hls/{sid}?u=...` является непрозрачным идентификатором ресурса этой
сессии. Подписанные адреса CDN, cookies и заголовки источника хранятся на
сервере. Произвольный адрес в `u` не разрешает доступ к нему.

## Сессия и сетевой профиль

Каждая сессия получает отдельный настоящий браузерный контекст. Плейлисты,
сегменты, HTTP-заголовки профиля, TLS и HTTP/2 обслуживает тот же нативный
браузер. Python получает тело ответа через browser fetch и DevTools.
UA, Client Hints и Origin вручную не подменяются. В запрос добавляются только
наблюдаемые сессионные заголовки источника и запрошенный Range.

Браузер остаётся открытым на протяжении сессии. WebSocket создаёт сам
исходный плеер. Heartbeat отправляется каждые 15 секунд. Сообщения
`config_update` обновляют сессионный заголовок `accepts-controls`. Закрытие
сессии, истечение 15 минут или shutdown закрывают контекст, WebSocket и
браузер. Смена озвучки закрывает предыдущую сессию и создаёт полный новый
bootstrap с новым `sid` и `active_id`. Старый `sid` после этого возвращает 404.

`active_id` идентифицирует инициализацию источника. Используется опубликованный
источником идентификатор, когда он присутствует. Для версий плеера без такого
поля назначается отдельный случайный идентификатор инициализации.

Кандидат Chromium берётся из подписанного Debian security release. Проверяются
подпись InRelease, SHA-256 индекса, версия и SHA-256 пакетов. Обновлённые бинарники
распаковываются в кэш сервиса. Дополнительный кандидат использует нативный
Chromium из официального манифеста установленного релиза Playwright. Версия
реально запущенного браузера проверяется перед открытием источника. Активным
профиль становится после подтверждённого чтения медиасегментов.

Пул содержит до 12 профилей: исходный и пять дополнительных на каждый
проверенный браузерный канал. Каждая сессия запускается в отдельном чистом
контексте Chromium. Профили одного канала используют один проверенный бинарник,
его нативные сетевые параметры и общий внешний IP Oracle. Пул хранит отдельное
состояние для каждого профиля и не меняет сетевой отпечаток вручную.

После отказа сессия закрывается без повторного запроса тем же профилем.
Следующий `/resolve` автоматически выбирает доступный профиль и создаёт
сессию заново. Для отказавшей пары iframe и профиля действует пауза 120 секунд.
После трёх отказов профиль помещается в карантин на 15 минут. После 18 успешных
сессий сервис выводит профиль из ротации и сразу создаёт следующее поколение
в том же слоте. Уже открытая сессия сохраняет прежний профиль до закрытия.
Новое поколение наследует карантин и паузы для отказавших iframe, получает
собственный идентификатор и проходит обычную проверку медиасегментов.
Состояние слота переживает рестарт. При запуске сервис также пополняет
слоты, исчерпанные в предыдущей версии. Параллельные инициализации
резервируют места в лимите 18.

Сервис сверяет релизы при запуске и раз в час. При временном сбое проверки
повторяет её через минуту и сохраняет кандидатов уже проверенного канала.
Обновление подписанного пакета Debian автоматически добавляет новое поколение
профилей. Для Playwright используется официальный релиз установленного пакета.
Когда все профили в карантине, сервис возвращает 409.

## Проксирование и ограничения

Перед выдачей каждого качества проверяются медиаплейлист, init-фрагмент при
его наличии и первый медиасегмент. Поддерживаются отдельные аудиоплейлисты
и byte ranges. HTML, пустые ответы и неподдерживаемое шифрование отвергаются.
Переписываются обычные URI и URI внутри HLS-тегов, включая карту инициализации,
аудиодорожки, субтитры и ключи обычного AES-128.

Два разрешения удерживаются на протяжении живых сессий, включая инициализацию.
Третий запрос ждёт до 30 секунд и затем получает 503 с `Retry-After: 30`.
Все обращения к источнику используют общий интервал не менее 0,5 секунды.
Сегменты сохраняются на диск на 60 минут. Ключ включает SHA-256 URL, а для
частичного ответа также диапазон. Полный ответ и частичный ответ не смешиваются.
Размер кэша ограничен 512 МиБ. Ошибочные ответы не кэшируются.

При запросе отсутствующего качества выбирается ближайшее доступное снизу,
либо минимальное доступное, если нижнего нет. Заголовки `X-Alloha-Quality` и
`X-Alloha-Degradation: quality-unavailable` сообщают результат без изменения JSON.

| HTTP | Условие |
| --- | --- |
| 404 | SID истёк или ресурс не принадлежит сессии |
| 409 | Отказ сессии источником или отсутствие доступного профиля |
| 502 | HTML, пустой ответ, неверный плейлист или ошибка источника |
| 503 | Два потока заняты дольше 30 секунд либо сервис останавливается |
| 416 | Некорректный или отсутствующий byte range |
| 422 | Входная ссылка не является поддерживаемым публичным iframe Alloha |

## Данные и проверки

Все файлы находятся в `$DATA_DIR/.codex-local/alloha-delivery/`.
`profiles/` хранит проверенные релизы, бинарники и состояние профилей.
`segments/` содержит ограниченный кэш. `logs/requests.log` содержит JSON-строки
с SID, профилем, внешним адресом, HTTP-кодом и хостом источника. Подписанные URL
и значения токенов в лог не записываются. Лог ротируется, три файла по 4 МиБ.
`ALLOHA_EXTERNAL_ADDRESS` позволяет задать известный публичный egress; иначе
он определяется один раз при первом запуске.

Контрактные тесты `tests/test_alloha_delivery.py` используют поддельный источник
и отдельно проверяют ограничение сессий, смену аудио, ответы HTML вместо сегмента,
отказы, карантин, вывод профиля из обращения, TTL, кэш и закрытие ресурсов.
Они не подтверждают доступность внешнего CDN. Живые проверки на Oracle используют
настоящий iframe «Резе», браузерный fetch и hls.js из зависимости проекта.
Нейросетевой inference в сервисе отсутствует.

## Живая проверка 6 ноября 2026

На Oracle ARM64 проверен опубликованный iframe «Резе» с выбранным дубляжом.
Resolver вернул три аудиодорожки с шестью качествами каждой, включая 2160p,
два субтитра и интервал пропуска. Все выданные качества прошли проверку init
и настоящего первого медиасегмента. Полная подготовка занимала около 40 секунд.

Обычный hls.js декодировал видео 3840×1604 и прошёл отметку 63 секунды без
фатальных ошибок. Перемотки на 300 и 15 секунд продолжили воспроизведение
без HTTP-ошибок. На холодном headless-клиенте возникали нефатальные события
bufferStalledError с последующим восстановлением.

Подмена подписи в настоящем CDN-URL вызвала 409. Следующий запрос создал
рабочую сессию за 38 секунд. Подстановка произвольного значения только в
accepts-controls не вызвала отказа этого CDN, поэтому такой запрос не
использовался как подтверждение проверки испорченной подписи.

Смена аудио вернула 200 после перехода на новый SID и выбрала в нативном
плеере audioId 2. После shutdown осталось ноль сессий и незавершённых закрытий.
Лимит двух потоков, третий ответ 503 после ожидания, TTL и счётчики профилей
дополнительно проверены изолированными контрактными тестами.

FFmpeg прочитал 60 секунд через прокси без перекодирования. Его перемотка
AV1 на этой сборке завершалась ошибками разбора temporal unit. Отдельный
ffplay с виртуальным SDL-выводом не завершился за 110 секунд и был остановлен.
Это не считается пройденным ffplay-критерием. Подтверждённая проверка
декодирования и перемотки выполнена настоящим hls.js/Chromium.

## Реальное состояние просмотра и восстановление

Только подготовленные сессии Alloha возвращают `playbackTelemetry: true`.
Наш React-плеер передаёт владельцу сессии через `POST /online/{sid}/playback`
фактическое время, паузу, скорость, перемотку, буферизацию и окончание видео.
События отправляются сразу, периодический снимок — раз в 10 секунд. Одновременно
выполняется один запрос; накопившиеся события заменяются последним состоянием.
После закрытия плеера обработчики и запросы удаляются.

Нативная браузерная сессия передаёт эти значения в WebSocket самого Alloha:
`resumed`, `paused`, `ended` и периодический `playing`. Время не увеличивается
искусственно. Без актуальных данных клиента heartbeat сообщает паузу.
Endpoint проверяет владельца и поля состояния; качество берётся из серверной
сессии. Абсолютный TTL 15 минут сохраняется, heartbeat его не продлевает.

Истечение сессии, закрытие её WebSocket или ответы 404/409/410 медиаресурса
запускают повторную подготовку Alloha. Плеер сохраняет последнюю позицию,
Play/Pause, эпизод, озвучку и качество; HTML video остаётся тем же элементом.
Повторные сигналы об одной истёкшей сессии объединяются в одно переподключение.
Если новая подготовка не удалась, остаётся ручная кнопка повтора.
Это восстановление после сбоя, а не гарантия отсутствия блокировок CDN.

Проверки этой интеграции: 17 Python-тестов с поддельным источником, 24 Node-теста
состояния/lease/модели плеера; отдельный браузерный тест с настоящим локальным
HLS-декодированием и поддельным API подтверждает восстановление во время Play,
на паузе и после HTTP 409 сегмента без замены video. Эти тесты не являются
проверкой внешнего CDN. На настоящем iframe Oracle отдельно подтверждена отправка
WebSocket-сообщений `resumed` на 120 с и `paused` на 137 с при скорости 1.25,
качестве 2160p и последующая доступность плейлиста. ML в этих проверках не используется.


## Импорт Alloha в зашифрованный Google Drive

Очередь импорта использует `AllohaImporter` с тем же экземпляром `AllohaDelivery`
и его event loop, что и просмотр. Два разрешённых потока на внешний адрес — общий
лимит просмотра и импорта, а не отдельные два слота для каждого загрузчика.
Только iframe, распознанный `is_alloha_player`, получает маркер `alloha-native`.
Другие плееры сохраняют прежний resolver/downloader; локальный экспорт не меняется.

Сегменты получает нативный браузер действующей сессии. Импорт не копирует наружу
заголовки и не использует старый HTTP-загрузчик CDN. На импорт приходится один
запрос ресурса за раз и общий интервал не менее четырёх секунд между запросами
импорта. Сессия не изображает просмотр: её heartbeat сообщает паузу.
Профили, карантин и проверка первого сегмента используются общие.

После истечения TTL или отказа ресурса загрузчик закрывает прежнюю сессию,
выполняет полный resolve и продолжает с недостающей части. Озвучка и уже выбранное
качество сохраняются. Перед смешиванием частей проверяются порядок и длительности
сегментов, byte ranges, параметры шифрования, хэши init-сегментов и ключей.
Если состав изменился, текущий импорт останавливается вместо сборки неверного файла.
Повторы ограничены; недоступность всех профилей не запускает бесконечный цикл.

Части сохраняются с контрольными суммами в приватном
`TaskStore.directory/.codex-local/alloha-import/{task}/{episode-hash}/`.
После ошибки задания их можно использовать при продолжении. Подписанные URL,
токены и cookies в checkpoint не записываются. Части являются временными исходными
медиа, а не Drive-файлами. После успешной зашифрованной загрузки checkpoint удаляется;
оставшиеся старше семи суток удаляются при запуске сервиса.
Сборка MP4 выполняется существующим ffmpeg `-c copy`, затем существующий VaultDrive
шифрует и загружает файл. Одновременной загрузки в Drive во время скачивания нет.

Проверки: 23 Alloha-контрактных/интеграционных теста и 10 проверок прежнего импортера.
Новые тесты используют настоящие FFmpeg HLS/remux и AES-GCM, но поддельные браузерный
источник и Drive. Проверены отдельное аудио, отказ, истечение сессии, продолжение
checkpoint, несовместимость нового потока, шифрование и пропуск уже сохранённого файла.
На настоящем iframe «Резе» новый адаптер скачал первые два медиасегмента и собрал
12,388 с MP4 3840×1604 со звуком (16,5 МБ, около 15 с вместе с подготовкой).
Это ограниченная живая проверка транспорта: полный фильм и запись в настоящий
Google Drive этой проверкой не подтверждаются. ML inference здесь отсутствует.
