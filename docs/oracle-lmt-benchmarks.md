# Полный LMT на Oracle A1

Замеряется цепочка Comic Text Detector → Manga-OCR → собственный Qwen3 4B →
LaMa → набор русского текста. Апскейл выключен.

## Окружение и вход

- Oracle A1 Flex: 2 OCPU / 2 CPU, 12 ГБ RAM, aarch64, без GPU и swap.
- Qwen3-4B-Q4_K_M через официальный llama.cpp b11887, CPU 2 threads,
  context 4096, parallel 1, reasoning off.
- LMT использует настоящий upstream ONNX-пайплайн в приватном Chromium.
- LLM и LMT находятся в отдельной Docker-сети, без публичных портов.
- Лимиты контейнеров: LMT 6 ГиБ, LLM 4 ГиБ; оба ограничены 2 CPU на той же VM.
- Перед запуском ожидаются load1 ≤ 1,5 и MemAvailable ≥ 10 ГиБ, не более 180 с.
- Рабочие контейнеры importer и HTTPS не перезапускаются. Данные измерений
  отделены от production volume в `/opt/mediavault-reader-bench`.

Вход — upstream `docs/images/raw-sample.jpg`, 1715×2417, 865285 байт,
3 области текста. SHA-256:
`56ed1dde6e8d880f1db136d1b2861262449b7311c5eefa9454c59613f347ea37`.
Source revision LMT: `39a95be1890e2ea3e227052976bbaf576a8eb7b3`.

## Подтверждённые попытки

| Конфигурация | Наблюдение | Готовая страница |
| --- | --- | --- |
| Первый запуск после подготовки | Проверка нагрузки отложила задание; инференс не стартовал | Нет |
| LMT 4 ГиБ + LLM 4 ГиБ, `a843937` | Docker `OOMKilled=true` на Manga-OCR; 41,749 с до ошибки | Нет |
| LMT 6 ГиБ + LLM 4 ГиБ, `a5cc23c` | Два прохода завершены, контейнер LMT: exit 0, `OOMKilled=false` | Да |

У неуспешного прогона сумма RSS дерева LMT достигла 5 168 779 264 байт.
Она может превышать cgroup limit из-за повторного учёта общих страниц памяти.
Это не время готовой страницы и не показатель пропускной способности.
LLM успешно загрузился; его контейнер не был убит OOM. После сбоя оба временных
контейнера остановлены и удалены; логи и отчёт сохранены отдельно перед повтором.

Команда полного успешного прогона, включая подготовку окружения, заняла
5 мин 37,586 с. Это не задержка одной страницы.

## Времена успешных проходов

Измерено 26 октября 2026, `a5cc23c`; оба прогона имеют `success=true`.

| Этап, секунды | Первый проход процесса | Повтор той же страницы |
| --- | ---: | ---: |
| Детекция CTD | 22,69 | 13,74 |
| Manga-OCR и script gate | 31,13 | 13,75 |
| Qwen3 4B, перевод | 62,25 | 63,66 |
| LaMa, инпейнт | 52,48 | 37,74 |
| Набор текста | 0,81 | 0,74 |
| Вся серверная обработка | **173,160** | **130,647** |

На каждом проходе: 3 переведённые области, LaMa — 3/3, fallback — 0.
Разница между суммой этапов и общим временем включает запуск Chromium,
декодирование и передачу буферов внутри backend. Ожидание очереди API и передача
изображения от пользователя в эту длительность не входят.

В повторном проходе перевод занимает около 48,7% общего времени, LaMa — 28,9%.
На данной конфигурации полную цепочку следует рассматривать как фоновую
обработку: примерно 2 минуты 11 секунд на эту страницу с прогретыми моделями.

Пики суммы RSS дерева LMT: 4997 МиБ на первом проходе и 4282 МиБ на повторном;
это метрика с повторным учётом общих страниц и без отдельного LLM.

Во время повторного перевода снят следующий Docker stats snapshot:

| Процесс | CPU | Память в снимке |
| --- | --- | --- |
| LMT | 2,57% | 3,692 ГиБ / лимит 6 ГиБ |
| Qwen3 4B | 193,83% | 3,181 ГиБ / лимит 4 ГиБ |
| Рабочий importer | 0,17% | 763,3 МиБ |
| Рабочий HTTPS | 0% | 40,41 МиБ |

MemAvailable VM в этом снимке — 3,64 ГиБ. Пик cgroup памяти LLM за прогон —
3 420 274 688 байт (3,185 ГиБ). Значения снимка не являются пиками LMT.
После измерения остались только рабочие контейнеры; `/health` ответил,
версия сервера — 11. Последний WebP-результат имеет размер 548004 байт.

Русский текст в трёх областях получен, но 4B переводит буквально и теряет
детали сцены. Успех измерения не является подтверждением готового качества
перевода для публикации.

Для кода этого прогона [Linux CI](https://github.com/Onikri/MediaVault/actions/runs/40282685055)
прошёл сборку, Node/Python и браузерные проверки. Они проверяют контракты;
цифры в таблице получены отдельным реальным инференсом на A1.

## Что входит в измерение

`wallSeconds` — длительность обработки страницы, включая запуск Chromium и
загрузку отсутствующих моделей, но без Docker build, скачивания GGUF и запуска
LLM-сервера. Разбиение этапов берётся из самого LMT: detection, OCR, translation,
inpaint, typeset. Метод очистки фиксируется для каждой области: при переходе с
LaMa на Fast это видно в счётчике fallback.

Первый прогон процесса не равен полностью пустому дисковому кешу. Веса,
успевшие сохраниться до OOM, используются повторно. Второй прогон выполняет
обработку той же страницы с прогретыми моделями и контекстом перевода; это не
попадание в кеш готового результата читалки.

`peakProcessTreeRssBytes` — сумма RSS Python, драйвера и дочерних процессов
Chromium с опросом каждые 50 мс. Общие страницы учитываются повторно. Отдельный
LLM-контейнер в эту величину не входит. Его `memory.peak` — другая метрика cgroup,
включающая файловый кеш; складывать её с суммой RSS как точный расход RAM нельзя.

Два прогона одной страницы дают базовую задержку, но не p95 и не нагрузочный
предел сервиса. Для готовности результата требуются `success=true`, непустое
изображение, перевод областей и проверка фактического метода инпейнта.

## Воспроизведение

На авторизованной VM, из сохранённого checkout нужного полного SHA:

```sh
bash deploy/oracle/benchmark-reader.sh <SHA> prepare-lmt
bash deploy/oracle/benchmark-lmt.sh <SHA> prepare 4b
bash deploy/oracle/benchmark-lmt.sh <SHA> lmt 4b
```

Полный отчёт: `/opt/mediavault-reader-bench/data/benchmark/lmt-4b-a1.json`.
Для короткого вывода OCI:

```sh
python scripts/summarize-reader-benchmark.py /opt/mediavault-reader-bench/data/benchmark/lmt-4b-a1.json
```

Неуспешное измерение сохраняется с `success=false`, последним этапом и временем
до ошибки. Не следует повторно запускать задание по одному лишь таймауту чтения
OCI: сначала проверяется существующий command execution и сохранённый отчёт.
